# 二阶段晋升提示词规范

> **校对基准**：`presets/two-stage-promotion/tool-bootstrap.mjs`、`presets/two-stage-promotion/agent.cordis.yml`、`presets/two-stage-promotion/custom-bash.mjs`
> **上游来源**：[xiaobright/dsh-anchored-standard](https://github.com/xiaobright/dsh-anchored-standard)（MIT），本仓库在其之上扩展了「一阶段隔离（quarantine）」与稳定化控制
> **本文档原则**：参数名与行为描述一律以代码为准；文档与代码冲突时改文档。第六章末尾列出**在本仓库中不存在**的参数名。

## 一、规范概述

「二阶段晋升」把一次会话切成两个输入面：先用最小输入面拿到「首轮推理轨迹」，拿到后再解锁完整能力。

| 维度 | 一阶段（锚定 / Anchor） | 二阶段（晋升 / Promoted） |
|---|---|---|
| System Prompt | 仅 persona 段（一行，46 字符） | 恢复全部 section，并在 persona 末尾追加工作目录行（`code` 呈现下再追加 PTC 说明） |
| 工具面 | 平台 `bash` + `str_replace_editor` | `code` 呈现：单个 `run_code`（PTC Mode）；`native` 呈现：完整原生工具目录 |
| 运行时上下文 | 清空（无 sandbox / approval 快照） | 正常上下文 |
| 消息来源 | 白名单（`user` + `goal`） | 全部来源 |
| 输出预算 | `bootstrapMaxTokens` 限制，晋升后剥离 | 不受一阶段预算限制 |
| 阶段目的 | 获得极简形态的首轮推理轨迹 | 拿到轨迹后解锁完整工具链与知识源 |

社区观测（非本仓库实测，仅供参照）：该形态在社区评测中报出高于默认预设的得分。本文档只规定「怎么做」，不背书具体分数。

## 二、晋升触发机制

### 2.1 阶段判定的唯一依据

一阶段 ⇔ 该会话的持久事件日志中**尚未出现 `tool/call` 事件**。

### 2.2 晋升信号的四个分支

| # | 条件 | 相关参数 | 行为 |
|---|---|---|---|
| 1 | 首个持久化 `tool/call` 且推理已锚定 | `anchorGate` | 立即晋升 |
| 2 | 已发生工具调用但推理未锚定 | `anchorGate` + `maxBootstrapSteps`（默认 4） | 第 4 步兜底晋升，避免无限期停在两工具形态 |
| 3 | 首轮响应未调用工具 | `promoteAfterFirstResponse` | 响应完成后晋升 |
| 4 | 锚定门未通过且首个 turn 结束 | `promoteAfterFirstResponse` | `turn/end` 释放，避免永久两工具会话 |

**锚定判定（`classifyReasoning`）**：取每条 assistant 消息的首个 reasoning 块（同一消息内后续块不翻案；一旦某条消息判为已锚定即锁定，不再回退）——

- 含 `we` 且不含 `let me` → minimal-like（已锚定，放行晋升）
- 含 `let me` → standard-like（未锚定）
- 其余 → 不确定（等待兜底）

`anchorGate` 默认关闭，本预设显式开启。该判定只决定「轨迹形态」，不用于识别模型身份。

### 2.3 状态持久化：没有独立的「晋升事件」

阶段状态由持久事件日志重建，不写额外事件。重建依赖的事件：`tool/call`、`assistant/message`、`step/start`、`turn/end`、`compaction/end`。因此 resume / reload 后的阶段判定与进程内一致。

### 2.4 压缩（compaction）后回到受控阶段

压缩会重写整个模型可见面，所以**压缩后的第一个请求是「第二个首轮请求」**：

- 会话回退到受控阶段 = 引导工具对（`shellTools` + `commonTools`）+ `compactionTools`（核心工作集）
- `code` 呈现下释放 PTC，直到边界之后出现**新的**晋升信号才重新晋升

### 2.5 首轮上下文隔离

- `messageSources` 白名单（默认即 `[user, goal]`）：被过滤掉的轮次不会触达模型——上游 issue #578 记录，否则 `/goal` 的 resume/pause 会死锁
- 运行时上下文清空；prompt 只保留 persona section（plan-mode 的 `plan:policy` 在晋升后才恢复生效）
- `bootstrapMaxTokens` 限制一阶段输出预算，晋升后剥离，避免预算被「焊死」到后续请求

## 三、提示词设计规范

### 3.1 一阶段：极简锚定

- persona 只有一行：`You are a helpful software engineer assistant.`
- **默认不加任何额外指令**。`phase1FirstCallInstruction` 是 opt-in（上游 issue #274），本预设**未设置**；它属于「偏离 byte-exact Minimal 表面」的实验性开关，不是规范默认值。
- 一阶段提示词风格：陈述式、无祈使句、无工具说明、无流程指引。

### 3.2 二阶段：晋升后的呈现

- `promotedPresentation: code`（**本预设取值**）→ 线上面只出现一个 `run_code`（PTC Mode），完整工具目录由生成的 SDK 承载；切换发生在 step 边界，不打断当前 step 已在进行的原生调用。
- `promotedPresentation: native`（**schema 默认**）→ 直接暴露完整原生工具目录。
- **重要更正**：晋升后 persona 正文不变，但会
  1. 恢复全部 prompt section；
  2. 在 persona 末尾追加会话工作目录行（`Your working directory is <cwd>.`）——让 agent 知道工作区，也让 plan-mode 的 `plan:policy` 真正生效；
  3. `code` 呈现下追加 PTC 说明段。

  因此「system prompt 全程字节不变」不成立。准确表述是：**一阶段只暴露 persona 段；晋升后在 persona 末尾追加环境行并恢复其余 section**。

### 3.3 中性措辞与知识注入

- `instructionHint`（本预设开启，issue #388）：晋升后注入**一次性、非命令式**提示——「参考文件位于这些路径，按需读取」——替代 AGENTS.md 全文注入。上游 #49 的 E1/E1.5/E2 实测显示，全文注入会翻转已锚定的轨迹。
- 知识仍可经 `read` / `skill` 按需触达。
- 延迟注入：`deferredSources: [agent-instructions, skill-catalog]` + `deferredGraceSteps: 1`，让晋升后的第一个请求保持干净。

## 四、单轮提示词模板（含用户输入）

> 一轮 = 一次用户输入触发的模型请求。模板只列模型可见内容：system 段 + 该轮注入的 messages；`<...>` 为占位符，见 4.6。工具面与过滤逻辑均由插件钩子决定，勿手写。用户侧输入该怎么写（正例 / 反例），见第五章。

### 4.1 一阶段轮（首次用户输入）

```text
[system]
You are a helpful software engineer assistant.

[messages]
1. user: <用户输入>
```

| 项 | 取值 |
|---|---|
| system 段 | 仅 persona（`PERSONA_SECTION_NAMES`） |
| messages | 仅 `messageSources` 白名单（`user` / `goal`） |
| 被剔除的 kind | `agent-instructions`、`skill-catalog` 及其它 |
| 运行时上下文 | 清空（`contexts: []`） |
| 工具面 | 平台 `bash` + `str_replace_editor`（压缩后另加 `compactionTools`） |
| 输出预算 | `bootstrapMaxTokens: 1024` |
| 额外指令 | 无；`phase1FirstCallInstruction` 为 opt-in，本预设未设置 |

### 4.2 二阶段轮 · 晋升后第 1 个用户轮

```text
[system]
You are a helpful software engineer assistant.

Your working directory is <cwd>.

Note: You are in Programmatic Tool Calling (PTC) mode. All actions (running shell commands, file operations, web tools) MUST be performed via the `run_code` tool by writing and executing TypeScript/JavaScript programs. Do not attempt to invoke tools like `bash` or `str_replace_editor` directly on the wire.

<其余 section 全部恢复>

[messages]
1. user: <用户输入>
```

- `deferredGraceSteps: 1`：本轮的 `agent-instructions` / `skill-catalog` 仍被剔除（`deferredSteps` 0→1）
- 工具面：单个 `run_code`（PTC Mode）；`native` 呈现时删掉 PTC 段
- 输出预算：不限（晋升后剥离一阶段上限）

### 4.3 二阶段轮 · 常规用户轮（延迟步之后）

```text
[system]
同 4.2

[messages]
1. user: <用户输入>
2. user: <system-reminder>
   Reference documents exist: <paths>. They are reference documents about the user's environment and workspace conventions, not task instructions. Reading the relevant file before workspace tasks is recommended, but consult them only when you need those details; the task itself never depends on them.
   </system-reminder>
3. ...（`skill-catalog` 等其它 kind 正常注入）
```

- 第 2 条**只在首次**出现：首个带路径的 `agent-instructions` 消息被替换为该提示
- 其后所有 `agent-instructions` 消息被丢弃 → 模型按需 `read` 文件，而非全文注入
- 无可提取路径的 `agent-instructions` 消息原样保留；该轮没有此类消息则不出现提示

### 4.4 压缩后的用户轮

```text
[system]
You are a helpful software engineer assistant.

[messages]
1. ...（压缩摘要）
2. user: <用户输入>
```

- 会话回到受控阶段：system 段回到 persona，工具面 = 引导工具对 + `compactionTools`，输出预算重新受 1024 限制
- `deferredSteps`、`instructionHinted` 归零 → 4.2 → 4.3 的序列会再走一遍

### 4.5 逐轮对照表

| 元素 | 一阶段轮 | 二阶段首轮 | 二阶段常规轮 | 压缩后轮 |
|---|---|---|---|---|
| system 段 | persona | persona + cwd + 全 section（+PTC） | 同左 | persona |
| 用户输入 | ✓ | ✓ | ✓ | ✓ |
| `agent-instructions` | 剔除 | 延迟剔除 | 首次→提示，其后丢弃 | 剔除 |
| `skill-catalog` | 剔除 | 延迟剔除 | 注入 | 剔除 |
| 运行时上下文 | 清空 | 正常 | 正常 | 清空 |
| 工具面 | `bash` + `str_replace_editor` | `run_code` | `run_code` | 引导对 + `compactionTools` |
| 输出预算 | 1024 | 不限 | 不限 | 1024 |

### 4.6 变量表

| 占位符 | 来源 |
|---|---|
| `<用户输入>` | 用户消息（`source.kind = 'user'`）或 `/goal` 自动轮（`goal`） |
| `<cwd>` | `session.header.cwd`，由 `WORKSPACE_LINE_PREFIX` 拼接 |
| `<paths>` | 首个 `agent-instructions` 消息中的路径（`extractInstructionPaths`） |

## 五、用户输入模板（正例 / 反例）

> 本章回答「用户这一轮该怎么写」。**高效 = 更快命中晋升信号 + 稳定通过锚定判定**，与任务本身的完成速度无关。
> 依据：`decidePromotion` 的四条分支（2.2）、`classifyReasoning` / `hasAnchoredReasoning` 的判定规则（2.2）、一阶段动作面（5.2）。

### 5.1 用户输入为什么影响晋升

- 晋升判定**不读取用户文本内容**——`decidePromotion` 只看 `toolCalled` / `anchored` / `steps` / `turnEnded`，因此不存在「触发晋升的关键词」。
- 用户输入经由三个中间量间接生效：

| 中间量 | 由输入决定的部分 | 影响的分支 |
|---|---|---|
| 是否产生 `tool/call` | 请求是否落在 `bash` / `str_replace_editor` 能闭环的动作上 | 2.2 的 #1 / #2 / #4 均要求有调用；仅 #3 允许无调用 |
| 首段 reasoning 形态 | 单目标收敛式 vs 多目标规划式 | `classifyReasoning` 判 minimal-like 与否 |
| 探索步数 | 路径是否明确、范围是否钉死 | `maxBootstrapSteps: 4` 兜底前的等待步数 |

- 一阶段的**任务信号 100% 来自用户输入**：system 只有 persona 一行、`messageSources: [user, goal]`、工具面两项、`bootstrapMaxTokens: 1024`。没有 AGENTS.md、没有技能目录、没有运行时上下文可以稀释输入质量。
- 判定窗口只有「首段 reasoning」：`hasAnchoredReasoning` 用 `find` 取首个 reasoning 块，同一条消息内后续块不能翻案；但**跨消息不锁定**——下一轮输入收敛后，新消息的首段可以是 `we …`，锚定即置位。因此输入质量影响的是**延迟的轮数**，而非能否晋升。

### 5.2 一阶段动作面（写输入前必读）

| 想要的动作 | 一阶段可用形态 |
|---|---|
| 读文件 | `str_replace_editor`（`view`）或 bash `cat` |
| 写 / 改文件 | `str_replace_editor`（`create` / `str_replace` / `insert`） |
| 搜索定位 | bash `rg` —— **阶段一没有 `grep` / `glob` 工具** |
| 运行命令 / 测试 | bash |
| 版本控制 | bash `git` |
| `read` / `write` / `edit` / `todo_write` / `ask_user_question` / `web_search` / 子代理 | ❌ 阶段一不可用（`compactionTools` 只在压缩后的受控阶段出现） |

输入里点名一个阶段一不存在的工具，会让模型先试错再绕行，白耗一步。

### 5.3 输入骨架

```text
<动词> <明确路径 / 符号>，<单点要求>。
产出：<产物形态>。
限制：不要 <禁止动作>。
验收：<命令或检查方式>。
```

- 硬约束：**单目标** · **动词开头** · **明确路径 / 符号** · **明确产物**
- 软约束：显式「不要做什么」· 给出验收命令
- 高风险措辞：`先…再…然后…最后…` 这类流程式引导是 `let me` 的头号来源，会把该轮钉在 standard-like 上。

### 5.4 正反例

#### 5.4.1 读取与理解

反例：

```text
这个项目是做什么的？架构怎么样？帮我梳理一下整体设计。
```

> 失效：无路径、无产物、纯知识问答 → 可能一次工具都不调（分支 #3）；「梳理整体设计」开放式多目标 → 首段推理易出现 `Let me start by exploring…`。

正例：

```text
读 lib/index.js，用 5 行以内说明它导出了什么，并给出 TWO_STAGE_GUIDANCE 的起止行号。
产出：5 行以内的要点 + 行号。
限制：不要读其它文件，不要改任何代码。
```

> 命中：单目标 + 明确文件 + 明确产物 → 一次文件读取即产生 `tool/call`，首段推理为 `we need to read …` → 分支 #1。

#### 5.4.2 单点修改

反例：

```text
帮我把提示词优化一下，看看哪里能改，顺便调整下格式。
```

> 失效：「优化一下 / 看看 / 顺便」= 无边界 + 多目标 → 首段推理展开规划（`let me`）；还会先探索多个文件，消耗步数。

正例：

```text
编辑 doc/二阶段晋升提示词规范.md 中 anchorGate 所在的那一行：把默认值改为 false，保持表格列对齐。
产出：只输出 git diff --stat。
限制：不要重写其它段落，不要调整章节编号。
验收：git diff --numstat 应只有 1 行改动。
```

> 命中：单一文件 + 单点改动 + 显式禁止 + 验收命令 → `str_replace_editor` 一次调用闭环。

#### 5.4.3 排障与运行测试（分两轮）

反例：

```text
有个报错，你看下怎么回事，能修就修了。
```

> 失效：无复现命令 → 模型先探索（列目录、猜测试文件）；「能修就修」= 授权扩大范围 → `Let me reproduce … then fix …`。

正例（第 1 轮 · 定位）：

```text
运行 node --test tests/tool-bootstrap.test.mjs，只报告失败的用例名和断言行。
产出：失败用例名 + 断言行原文。
限制：不要修改任何文件。
```

正例（第 2 轮 · 修复）：

```text
修复上一步失败的断言：编辑 presets/two-stage-promotion/tool-bootstrap.mjs，只改最小必要行。
产出：git diff。
限制：不要改测试文件。
验收：重新运行同一条 node --test 命令并通过。
```

#### 5.4.4 新增文件 / 新增功能

反例：

```text
给这个插件加个开关，可以控制晋升行为，最好还能配置。
```

> 失效：「开关 / 配置」是未定形的开放名词 → 模型先做设计推演（`let me design …`）；可能跨多文件，而一阶段输出预算只有 1024 token。

正例：

```text
在 presets/two-stage-promotion/agent.cordis.yml 的插件配置里新增一行 anchorGate: false，位置紧跟 maxBootstrapSteps。
产出：git diff。
限制：不要改其它键，不要动 tool-bootstrap.mjs。
```

#### 5.4.5 跨文件重构（必须拆轮）

反例：

```text
先分析 tool-bootstrap.mjs 的晋升逻辑，然后把命名统一一下，最后更新文档和 README。
```

> 失效：三重目标 + 顺序词 → 首段推理几乎必然是 `Let me first … then … finally …` → 直接判 standard-like，本轮无法锚定。

正例（拆成三轮，每轮一个目标）：

```text
第 1 轮：读 presets/two-stage-promotion/tool-bootstrap.mjs，列出所有配置键名及其默认值，不改代码。
```

```text
第 2 轮：只把 deferredGraceSteps 的默认值从 0 改为 1（仅该一行），产出 git diff。
```

```text
第 3 轮：在 doc/二阶段晋升提示词规范.md 的参数表中同步 deferredGraceSteps 的默认值，产出 git diff --stat。
```

#### 5.4.6 搜索定位（受工具面约束）

反例：

```text
用 grep 工具找一下所有用到 anchorGate 的地方。
```

> 失效：阶段一没有 `grep` 工具 → 模型先试调用失败再改用 bash，多耗一步。

正例：

```text
用 bash 运行：rg -n "anchorGate" presets lib tests
产出：文件名 + 行号 + 该行原文。
限制：不要读文件内容，不要改代码。
```

#### 5.4.7 提交与版本控制

反例：

```text
把改动提交一下。
```

> 失效：无范围、无提交信息 → 模型先 `git status`、再 `git diff`、再猜提交信息，3 步起步。

正例：

```text
运行 git add -A && git commit -m "Align promotion spec with implementation"，然后输出 git log --oneline -1。
产出：一行提交记录。
限制：不要 push。
```

#### 5.4.8 追问与追加约束（第二轮怎么写）

反例：

```text
嗯，但是我觉得这样不太好，你再想想，可能还有别的地方也要改，顺便看看有没有隐患。
```

> 失效：否定式开放追加 → 新一轮首段推理变成 `Let me reconsider …`。

正例：

```text
只改一处：把上一步改动里 anchorGate 的值改回 true，其余保持不动。
产出：git diff。
限制：不要重新分析其它参数。
```

### 5.5 反例特征词速查

| 反例特征词 | 后果 | 替换为 |
|---|---|---|
| 帮我看看 / 了解一下 | 无工具调用 → 分支 #3 | 读 `<路径>`，输出 `<产物>` |
| 优化一下 / 调整下 | 无边界 → 探索步数上升 | 编辑 `<文件>` 的 `<位置>`，只改 `<点>` |
| 分析一下 / 梳理整体 | 开放式 → `let me` | 列出 `<文件>` 中的 `<具体项>` |
| 先…再…然后…最后 | 多目标 → 必然 `let me` | 拆成多轮，每轮一句 |
| 顺便 / 还有 / 最好能 | 隐性多目标 | 留到下一轮 |
| 能修就修 / 尽量全面 | 授权扩大 → 发散 | 只改 `<行>`，不要动其它 |
| 用 `grep` / `glob` / `read` 工具 | 阶段一不可用 → 无效步 | 用 bash 运行 `rg` / `cat` |

### 5.6 三条硬规则

1. **一轮一个目标**；
2. **动词开头 + 明确路径 + 明确产物**；
3. **用「限制：不要…」和「验收：…」把范围钉死**。

## 六、配置参数规范（以代码为准）

| 参数 | 本预设取值 | schema 默认 | 作用 |
|---|---|---|---|
| `shellTools` | `[bash]` | 必填 | 一阶段的平台 shell 工具 |
| `commonTools` | `[str_replace_editor]` | 必填 | 一阶段的通用编辑工具 |
| `messageSources` | `[user, goal]` | `[user, goal]` | 一阶段允许触达模型的消息来源 |
| `anchorGate` | `true` | `false` | 首个工具调用是否要求推理已锚定 |

| `promoteAfterFirstResponse` | `true` | `false` | 无工具调用的首轮响应后晋升；并在 `turn/end` 释放锚定门 |
| `bootstrapMaxTokens` | `1024` | 不限 | 一阶段输出预算，晋升后剥离 |
| `compactionTools` | `[read, write, edit, glob, grep, todo_write, ask_user_question]` | `[]` | 压缩后受控阶段的核心工具集 |
| `deferredSources` | `[agent-instructions, skill-catalog]` | `[]` | 晋升后延迟注入的知识源 |
| `deferredGraceSteps` | `1` | `0` | 延迟步数 |
| `promotedPresentation` | `code` | `native` | 晋升后呈现：单 `run_code` / 完整原生目录 |
| `instructionHint` | `true` | `false` | 非命令式一次性提示，替代全文注入 |
| `phase1FirstCallInstruction` | 未设置（注释保留） | 未设置 | 一阶段命令式首调用指令（opt-in，偏离项） |

补充：

- 一阶段的 `bash` 在 Windows 上由 `custom-bash.mjs` 提供 Git Bash 形态（`bashPath` 可显式指定；非零退出为上报而非抛出，且该路径无 OS 沙箱约束、状态不跨调用保留）。跨平台对齐时以「平台 shell + `str_replace_editor`」为准。
- 一阶段要求 `shellTools` 在当次组合中**恰好命中 1 个可用工具**；否则插件不退化为报错，而是回落到完整目录并给出一次性告警——组合漂移不允许锁死会话。
- 会话未选择工作区时，persona 保持裸一行（不追加工作目录行）；工作区切换后该行按会话头实时读取，不会过期。
- 插件名 `anchored-tool-bootstrap`，`inject: [systemPrompt, tools]`。

> ⚠️ **以下参数名在本仓库中不存在**（旧文档/其他预设残留，照抄会静默失效）：`promoteOn`、`residentTools`、`includeSubagents`、`includeHarnessIdentity`、`dev_tool_search`。

## 七、反模式与避坑

1. ❌ **一阶段暴露过多工具** → 保持 `shellTools` + `commonTools` 两项，不出现 `glob`/`grep`。
2. ❌ **一阶段注入命令式行动指令** → `phase1FirstCallInstruction` 是 opt-in 偏离项，默认关闭。
3. ❌ **晋升后注入 AGENTS.md 全文 / 「read first and follow them」式命令** → 改用 `instructionHint` 的中性措辞。
4. ❌ **首轮请求被运行时上下文污染** → 清空 `contexts` + `messageSources` 白名单。
5. ❌ **忽略压缩边界** → 压缩后必须回退受控阶段，否则「第二个首轮请求」失去锚定。
6. ❌ **假设晋升后 system prompt 字节不变** → 实际会追加工作目录行并恢复其余 section。
7. ❌ **照抄不存在的参数名** → 见第六章警告。
8. ❌ **用开放式多目标输入替代分轮输入** → 首段推理出现 `let me`，锚定门不通过，只能等 `maxBootstrapSteps` 兜底或 `turn/end` 释放（见第五章）。
